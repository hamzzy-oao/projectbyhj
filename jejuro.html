① 자동 저장이 다른 탭의 수정을 덮어씀

🚨

문제: 일정 화면은 변경 후 0.7초 뒤 자동 저장함. 같은 일정을 두 탭에서 고치면 나중에 저장된 탭이 앞 탭의 수정을 말없이 지움

🔍

원인: 저장 API가 “일정 전체 덮어쓰기” 방식 → 서버는 요청이 어떤 상태를 보고 만들어진 것인지 알 수 없음

해결

  1. 버전 만들기: 경로 이름 + 일차별 방문 순서를 SHA-256으로 해시해 응답에 version으로 내려주고, 저장 요청에 baseVersion으로 다시 받음 (DB 칸 추가 없음)
  2. 서버에서 비교: 여행 행을 SELECT … FOR UPDATE로 잠근 뒤 현재 버전과 비교, 다르면 409
    • 격리 수준은 READ COMMITTED로 지정함. REPEATABLE READ에서는 잠금 전 스냅샷을 읽어 비교가 틀어질 수 있기 때문
  3. 화면에서 처리: 409를 받으면 자동 저장을 멈추고 알림. 저장 못 한 변경은 sessionStorage에 보관하고, 다시 열었을 때 버전이 같을 때만 복구

✅

결과: 말없는 덮어쓰기 → “다른 화면(탭)에서 이 경로가 먼저 바뀌었어요” 알림 + 최신 경로 다시 불러오기

② 길찾기 API가 실패해도 일정 화면은 멈추지 않게

🚨

문제: 카카오모빌리티는 섬 · 산처럼 도로 탐색이 안 되는 곳에서 실패함 → 경로선 · 이동 시간 · 택시 요금이 비어 화면이 멈춤. 방문 순서도 사용자가 직접 맞춰야 했음

해결 A: 실패 시 추정값으로 대체

  • 카카오 호출 실패를 잡아 직선거리 × 추정 속도(40km/h)로 거리 · 시간 · 택시 요금 계산
  • 카카오 오류 메시지를 사용자가 이해할 수 있는 문장으로 바꾸고 “직선거리 추정값으로 표시”라고 명시
  • 섬(배편) · 산(주차 · 등산) 장소는 따로 안내

해결 B: 방문 순서 추천 (외부 API 없이 서버에서 계산)

  • 1번 방문지는 출발점으로 고정, 원하면 마지막 방문지도 고정. 기준은 직선거리 합이 가장 짧은 순서
순서를 바꿀 장소 수 방법 결과
8곳 이하 모든 순서 비교 (8! = 40,320가지, 즉시 계산) 정확한 최단 (EXACT)
9곳 이상 최근접 이웃으로 잇고 → 2-opt로 꼬인 구간을 뒤집어 짧아지면 교체 근사 (HEURISTIC)

✅

결과: 외부 API가 실패해도 일정 편집은 계속 동작하고, 계산 결과가 정확값인지 근사값인지 함께 알려 줌

③ 핵심 API 보안 테스트 (세션·CSRF 방어, 무차별 대입 차단, CSV 수식 주입 방어)

🚨

위험: 사용자 일정 및 계정 접근 시 비인가 탈취, CSRF 위조 요청, Brute Force 무차별 로그인 시도, 관리자 CSV 내보내기 시 악의적 수식 주입(CSV Injection) 위험

🔍

원인: API 엔드포인트의 권한 인가와 입력값 정규화, 레이트 리밋 검증이 사전에 철저히 검증되지 않으면 배포 환경에서 심각한 보안 결함 발생

해결

  1. Spring Security 세션 및 CSRF 보호: 동일 출처 리버스 프록시 환경에서 세션 쿠키(SameSite=Lax)와 CSRF 토큰 검증 (AuthControllerTest 8개)
  2. 무차별 로그인 시도 차단: IP/계정 기반 레이트 리밋 적용 (LoginAttemptLimiterTest 5개)
  3. 관리자 CSV 수식 주입 방지: 특수기호(=, +, -, @) 중화 처리 (CsvNeutralizeTest 2개)

✅

결과: 핵심 API 보안 테스트 15종 전원 통과, 인가 권한 침범 원천 차단 및 데이터 무결성 확보

🤖 AI 서버 연동 (내 담당 범위)

ℹ️

모델 자체(CatBoost 회귀, 입력 피처 76개, 후보 관광지 275곳, Recall@10 약 27.1%)는 팀장 담당. 나는 그 모델을 서비스에서 안정적으로 쓰도록 Spring Boot → FastAPI 연동을 맡음

1. 입력 변환

  • DB 설문 문항 → 모델 피처 이름 매핑 (문항 순서와 피처 순서가 달라 따로 관리)
  • 권역 · 동반자 코드를 모델 입력 형식으로 전달
  • 관심 없음 · 숨김 장소는 제외 목록으로 전달 → 빼고도 10곳 유지

2. 실패 대응

  • 연결 5초 · 응답 30초 제한, 실패는 502로 통일
  • 형식이 다른 응답을 “추천 0개 성공”으로 넘기지 않고 오류로 처리
  • 같은 여행의 동시 요청(새로고침 · 이중 호출)은 잠금으로 하나씩 처리
  • AI 호출 중에는 트랜잭션을 열지 않아 DB 연결을 붙잡지 않음

3. 기록 · 재사용

  • 요청마다 모델 버전 · 응답 시간 · 결과 수 저장
  • 여행당 한 번: 성공한 추천은 다시 열어도 같은 결과
  • 기록이 관리자 KPI와 재학습 데이터로 이어짐

🚀 배포 자동화 (CI/CD)

main에 push하면 응답 확인까지 자동으로 진행. 배포 완료 기준을 “서버가 실제로 응답할 때”로 잡음

  1. main push: GitHub Actions 실행, 배포가 겹치면 앞 배포가 끝난 뒤 진행
  2. EC2 접속 (SSH): 호스트 · 키는 GitHub Secrets로 관리, 최신 코드 받기
  3. 사전 검사: 비밀 설정 파일이 없으면 배포 중단
  4. 다시 빌드 · 실행: docker compose로 web · api · ai · db 4개 컨테이너, db 헬스체크 통과 후 api 시작
  5. 응답 확인: /api/auth/csrf 응답을 최대 3분 동안 확인하고, 응답이 오면 완료

설정 파일이 폴더로 바뀜 없는 파일을 컨테이너에 연결하면 Docker가 같은 이름의 빈 폴더를 만들어 이후 업로드가 꼬임 배포 첫 단계에서 파일 존재를 확인하고 없으면 중단
재배포 직후 502 api 컨테이너가 새로 만들어지면 Nginx가 예전 컨테이너 주소를 기억함 api를 다시 만든 뒤 web(Nginx)도 다시 시작

기술 고른 이유 직접 구현한 범위 확인 방법
Spring Security
세션 + CSRF 		화면과 API가 같은 주소 → 토큰을 브라우저에 저장하지 않는 쿠키 세션, 상태 변경 요청은 CSRF로 보호 3사 OAuth2 로그인 · 계정 연동 구현, 회원가입 · 로그인 문제 해결 (기본 기능은 팀장 구현) AuthControllerTest 8개
LoginAttemptLimiterTest 5개
JPA + 행 잠금 같은 여행에 저장 · 장소 빼기 · 확정 요청이 겹칠 수 있음 SELECT … FOR UPDATE, READ COMMITTED, 경로 버전 비교 동시성 단위 테스트는 아직 없음 → 다음 단계
FastAPI 분리 모델이 Python 기반이라 분리해, Spring과 장애 · 배포 단위를 나눔 HTTP 클라이언트, 타임아웃, 응답 검증, 실패 기록 RecommendServiceTest 3개
Docker Compose
GitHub Actions 		서버 4개를 한 EC2에서 같은 설정으로 다시 만들 수 있게 Dockerfile 3개, compose, Nginx 설정, 배포 워크플로 배포마다 응답 확인 자동화
관리자 KPI 추천 담기율 · 확정률 · 만족도를 모델 버전별로 비교 추천 기록 기반 집계, CSV 내보내기 CsvNeutralizeTest 2개 (CSV 수식 주입 방지)
